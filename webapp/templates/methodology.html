Method report

How the model was trained and adapted

This is the technical story behind the application. It covers the sample construction, masked financial-event modelling, the base checkpoint, and the small LoRA updates used for the two downstream tasks.

Sampling

Random cutoffs, trailing context

During pretraining, each training account receives a different random cutoff at each epoch. The model receives every transaction known by that cutoff, then keeps the most recent 256 events. Shorter histories remain shorter and are padded only when they are batched. This exposes the model to variable sequence lengths and changing positions in an account's life.

Objective

Masked financial-event modelling

A portion of event value tokens is replaced by a mask token. The model predicts the original value from the field key, the other event fields, profile state and the surrounding event history. In this project, the MLM head predicts value vocabulary IDs. It does not predict future transaction totals.

Time

The Czech timestamp quirk

The public source stores dates, not time-of-day timestamps. Same-day ordering is made deterministic with transaction ID. I use day-of-week and day-of-month cycles, but intentionally omit hour-of-day features instead of pretending the data contains them.

Adapters

Why LoRA is small

The base checkpoint stays frozen. LoRA adds two low-rank matrices to the History Encoder's Q, K, V and feed-forward projections. Its B matrix starts at zero, so an adapter begins as exactly the base model. Training changes only the adapter weights and a one-dimensional task head.

Pretraining trace

Masked-event loss across 300 epochs

The curve uses the committed checkpoint's metrics. Validation loss falls quickly, then flattens near the final value. The selected base checkpoint is the epoch with the lowest validation loss, not simply the final epoch.

What does and does not vary at inference time?

You can choose a cutoff and optionally a window start. The transaction sequence can therefore be shorter than 256 events or a different trailing slice of an account's history. The model was trained with variable lengths because some accounts had fewer transactions by their random cutoff. It was not trained on arbitrary fixed-duration windows as a separate augmentation. For a long selected range, the current checkpoint still uses the latest 256 events, because that is the maximum context it saw in pretraining.

Use the project

The website is only one interface

The repository also installs a Python package named pragma_lite. It contains the typed account records, train-fitted tokenizers, encoders, LoRA loading contract, and notebook helpers used by this site. The shipped Czech checkpoint is useful for reproducing this project; a new transaction schema needs its tokenizer fitted on that dataset's training split and its own pretraining run.

View the source repository on GitHub →

Use the Python library

From the repository root, install the project in editable mode. The same import path is used by the site, scripts and notebooks.

python -m pip install -e ".[notebooks,web]"
from pragma_lite import AccountTaskPredictor

predictor = AccountTaskPredictor.from_checkpoints(
    "app_assets/artifacts/models/checkpoints_swoll/pragma_lite_mlm/best.pt",
    "app_assets/artifacts/adaptors/future_value/future_value_lora_rank_04.pt",
)

The predictor binds the base checkpoint, its fitted tokenizers and one compatible adapter. It verifies that the adapter was trained for that exact base checkpoint before it accepts it.

Run the notebooks in VS Code

Open the numbered notebooks in notebooks/, select the repository's Python environment as the Jupyter kernel, then run them in order. They are deliberately thin interfaces over pragma_lite, so the model code remains importable and testable outside a notebook.

./FinBert/Scripts/Activate.ps1
python -m pip install -e ".[notebooks]"
code notebooks/02_pretrain_mlm.ipynb

On Windows PowerShell, use the activated FinBert environment as the notebook kernel.
