Architecture

Three encoders, one account embedding

The original PRAGMA paper uses a Profile State Encoder, an Event Encoder and a History Encoder. I kept that shape. The difference is scale and data scope: this model is a 1.59M-parameter version trained on one public banking dataset.

flowchart LR
  A["Account history\ntransactions through a cutoff"] --> B["Event tokenizer\nkey + value + time"]
  P["Profile state\nstatic fields + life-long events"] --> Q["Profile tokenizer\nkey + value + time"]
  B --> C["Event Encoder\n3 Transformer blocks\n[EVT] per transaction"]
  Q --> D["Profile Encoder\n3 Transformer blocks\n[USR] summary"]
  C --> E["Calendar projection\nday-of-week + day-of-month"]
  D --> F["History Encoder\n3 Transformer blocks + RoPE"]
  E --> F
  F --> G["Account embedding"]
  G --> H["MLM head during pretraining"]
  G --> I["LoRA adapter + task head"]

01

Structured tokens

A transaction is not converted into a sentence. Every field is kept as a pair: a key identifies the meaning, such as operation, and a value identifies the observed category. Amount and balance become train-fitted quantile buckets. This lets the model distinguish the number's range without inventing text tokens for digits.

02

Event and profile branches

The Event Encoder sees one transaction at a time and returns its learned [EVT] summary. The Profile Encoder processes static state and dated milestones, returning [USR]. Those pieces should not be treated as the same kind of timestamped data, which is why the profile branch carries its own time coordinates for life-long events.

03

History reasoning

The History Encoder receives the profile summary followed by event summaries. It is where transactions attend to each other across time. RoPE uses the paper's transformed gap-to-last-event coordinate, while calendar features are added to event summaries before this stage.
